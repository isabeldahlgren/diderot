# OpenAuthor — PLAN.md

> A preprint server where AI can be a disclosed co-author or sole author.
> Epistemic quality is not enforced — it is *signalled*, voluntarily, via certificates.

---

## 1. Philosophy

OpenAuthor is **permissive by default and transparent by design**. There are no bans on AI-generated content. There is no editorial gatekeeping. The only requirement is honest authorship disclosure. Readers decide what they trust.

The quality signal comes from certificates. Certificate issuers — journals, tools, reviewers, automated systems — bear reputational costs for issuing bad ones. Over time, a market of issuers will emerge, and readers will learn which issuers to trust. OpenAuthor does not pick winners. It is infrastructure: it stores and displays certificates neutrally, shows the issuer clearly, and gets out of the way.

Mechanism design is hard. Voluntary transparency is tractable. We do the tractable thing.

## 2. Core Concepts

### 2.1 Papers

A paper on OpenAuthor is a submission with:

- A **PDF** (primary artifact)
- Optional **source files** (LaTeX, markdown, code, data)
- An **author list** — each author tagged as `human`, `ai`, or `human+ai`
- A **metadata block** (title, abstract, subject area, date, version)
- Zero or more **certificates** (see §2.2)

Papers are versioned. Each version is immutable once submitted. A new version creates a new record linked to the previous one (like arXiv v1/v2/...).

### 2.2 Certificates

A certificate is a **structured, machine-readable attestation** attached to a paper. It is issued by a human — either an author of the paper (self-declared) or a third-party human reviewer.

**Only humans can add certificates.** AI agents cannot issue their own certificates. A pure AI-authored paper will have an empty certificate panel at submission; any human can add a certificate later, in which case they are tagged as the issuer.

OpenAuthor stores and displays certificates. It does not curate, endorse, or validate them beyond checking JSON schema conformance. Anyone can define a schema. Any human can issue a certificate. The display always shows the issuer prominently — readers judge provenance.

Each certificate record:

```json
{
  "certificate_type": "ai-disclosure",
  "schema_version": "1.0",
  "schema_url": "https://openauthor.org/schemas/ai-disclosure/1.0",
  "issuer": {
    "name": "AI Usage Cards",
    "url": "https://ai-cards.org",
    "issuer_type": "third_party_tool"
  },
  "issued_at": "2026-06-11T00:00:00Z",
  "self_declared": true,
  "payload": { ... }
}
```

`issuer_type`: `self` | `third_party_tool` | `human_reviewer` | `automated_system`

Certificates can be added to any paper version at any time. Post-publication additions are timestamped — readers can see when they were attached.

### 2.3 AI Authorship

```json
{
  "name": "Claude Sonnet 4.6",
  "author_type": "ai",
  "model_family": "Claude",
  "model_version": "claude-sonnet-4-6",
  "provider": "Anthropic",
  "contribution": "Proof search, draft writing"
}
```

`author_type`: `human` | `ai` | `human+ai`

There is no rule about ratios. A paper can have zero human authors.

## 3. Certificates (v1)

In v1, the only supported certificate type is an **[AI Usage Cards](https://ai-cards.org) export**. Authors paste or upload the JSON generated by ai-cards.org. OpenAuthor stores it verbatim and renders the known fields.

Other certificate types (formal verification, reproducibility, peer review, other disclosure standards) are left for post-v1. The data model is designed to accommodate them without schema changes.

## 4. Tech Stack

### Backend
- **Language**: Python (FastAPI)
- **Database**: PostgreSQL — papers, authors, certificates, versions
- **File storage**: Cloudflare R2 — PDFs, source files
- **Search**: Meilisearch

### Frontend
- **Framework**: Next.js (App Router)
- **PDF viewer**: PDF.js
- **Auth**: ORCID OAuth for humans; API keys for AI/automated submissions

### API

REST API so papers can be submitted programmatically — important for AI-authored submissions where no human is at a browser.

```
POST /api/v1/papers
POST /api/v1/papers/:id/certificates
GET  /api/v1/papers/:id
GET  /api/v1/papers/:id/certificates
GET  /api/v1/schemas
```

## 5. Submission Flow

### Human-authored or human+AI

1. Author logs in via ORCID
2. Uploads PDF + optional source files
3. Fills author list (add AI co-authors with model info)
4. A human author fills the AI disclosure certificate, or imports JSON from AI Usage Cards
5. Submits — paper is immediately public

### AI-authored (no human at keyboard)

1. API key authenticated request
2. Paper metadata + PDF + author list in one POST — no certificate
3. Immediately public with an empty certificate panel
4. Any human can later attach a certificate; they are tagged as issuer (`issuer_type: "human_reviewer"`)

---

## 6. Display

### Paper page

- Title, authors with type badges (`human` / `AI — Claude Sonnet 4.6 / Anthropic` / `human+AI`), abstract, date, version history
- **Certificate panel**: all attached certificates, each expandable, showing issuer, date, and full payload. No star ratings, no scores, no platform endorsement — just what was disclosed, by whom, when.
- PDF inline viewer
- Download links (PDF, source)
- BibTeX export

### Browse / feed

- Chronological feed of new submissions (like arXiv's new listings)
- Filterable by: authorship type, subject area, certificate presence
- Search by title, author, abstract

---

## 7. What OpenAuthor Does NOT Do (v1)

- No moderation or editorial filtering (except a minimal content policy — see §9)
- No quality scores
- No AI-detection
- No paywalls or submission fees
- No certificate validation beyond JSON schema conformance
- No enforcement of any disclosure standard

## 9. Open Questions

**Blocking for v1:**
- **Moderation floor**: no-moderation is clean in principle. In practice, CSAM or incitement could arrive. A minimal content policy (not epistemic, just legal) is needed before launch.
- **BibTeX / citation format for AI authors**: no standard exists. OpenAuthor should propose one for the first paper submission.

**Post-launch:**
- **ORCID for AI**: ORCID doesn't issue iDs for non-humans. Mint our own AI author identifiers?
- **Certificate spam**: open certificates mean anyone can issue a fake "peer reviewed" certificate. Primary mitigation: display always shows issuer URL prominently, readers judge. Secondary: schema registry can be curated over time if spam becomes a problem.
- **Long-term preservation**: consider early partnership with Internet Archive or a university library.
